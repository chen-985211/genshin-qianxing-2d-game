# AI 编码必读

文档版本 1.3 · 2026-10-05

适用范围：《原神》千星奇域的 2D 单人小游戏 Lua，使用电脑键鼠操作，通过客户端 UI 实现。

**每次开始编写或修改 Lua 前，必须完整读取本文件。** 适用于新建玩法、修复错误、调整视觉与手感、性能优化，以及信号、动效、音效等接入代码。小改动也先读取，再只应用与本次改动相关的要求。同一轮编辑中已经完整读取且文件未变化时可复用；新任务、上下文压缩后未保留全文或文件更新后，必须重新读取，不能仅凭 Skill 简介或历史摘要跳过。

本文集中维护 AI 编码要求。人的编辑器步骤见[操作指南](editor-guide.md)，任务引导与排错入口见 [SKILL.md](../SKILL.md)。本文件中的方法和参数需结合本次玩法使用；已验证的基础搭建流程不等于新代码已通过实机验证。

**官方成功结算是完整游戏的必选功能。** 无需用户再次提醒，AI 必须写好 Lua 中的实际接入逻辑，并在每次完整代码交付前检查通关到官方结算请求的调用路径。只声明信号名、保留空函数、显示自绘胜利页或提供服务端接线说明，都不满足要求。具体实现与检查见[输入生命周期与官方结算](#输入生命周期与官方结算)。

## 编码前的输入与接入约定

先读取当前 Lua（如有）及用户已提供的信息。默认只需两个真实模板根索引与玩法要求；确认的概念图、指定图片、声音资源和多动效用途按需补充。已知信息不重复询问，不要求人填写整套环境配置表。

缺少索引时可以先设计玩法和实现不依赖索引的逻辑，交付可直接试玩的代码前应补齐配置。用户明确要求自行填写时，标清待填项，不能伪造资源或索引。游戏逻辑不得写死为某个题材。

下列约定与操作指南配套。涉及编辑器位置和步骤时，查阅操作指南对应章节：

- **正式单人人数：**AI 必须指导用户按操作指南“先设置正式单人人数”配置关卡，上传前核对“当前可进关人数”为 1。只写单人 Lua、选择单人试玩或在玩法内忽略其他玩家，都不能代替正式人数限制；超限模式也可设置为单人。
- **模板根类型：**QX_Widget 的根为容器，直接子级为文本框和光标检测区域；QX_Image 的根为图片。两个 ID 都取模板根索引，不取子控件或脚本索引。
- **宿主与别名：**GameRoot 是内层“容器节点”的别名，不要求修改控件名称。主脚本只挂在这里，通过 `script.object` 获取。模板、文本框、图片和动效上不再挂同一份游戏主脚本。
- **文件操作顺序：**拿到 AI 的完整代码 → 新建客户端脚本 → 打开编辑器生成的关联文件 → 粘贴并保存 → 在 GameRoot 的脚本页签添加该脚本。使用“新建客户端脚本”，无需另建脚本映射。
- **结算配置：**`COMPLETE_SIGNAL` 使用 `MiniGame_Complete`，`SETTLEMENT_ACK_SIGNAL` 使用 `MiniGame_SettlementAccepted`，均无参数。在“服务器信号管理器”创建，在节点中点击搜索图标选择。
- **两处独立挂载：**客户端脚本挂在 GameRoot；服务端结算节点图添加到玩家模板的“玩家编辑 → 节点图”。默认布局无需重新绑定，并不代替添加节点图。以两个位置的列表可见为完成标志。
- **两类接线：**结算节点图既要白色执行线，也要“获取自身实体”到三个玩家输入的蓝色数据线，连接方式见操作指南第 4 步。创建、接线、保存后，继续操作指南第 5 步添加到玩家。
- **音效来源：**代码动画和资源音效分别处理。动效控件只是资源入口，需要 Lua 实现对应的事件触发逻辑；资源本身无声时，打开音效开关也不会产生声音。

上述约定用于本文的通用环境。若用户明确给出其他有效配置，先核对实际差异，不静默覆盖其配置或扩展任务范围。

## 通用设计与实现原则

新增玩法或较大改动时，用以下原则选择方案；小修只应用相关项，不要求用户重新走完整制作流程。它们指导 AI 的实现取舍，具体编辑器操作仍按指南执行。

1. **从玩家体验选择实现。** 先明确主要操作、目标和最重要的反馈，再选满足这些要求的简单模型。将“爽快”“清晰”“流畅”等要求落到可观察的行为，例如按下后立即出现反馈、主体轮廓可辨认、暂停恢复不跳动。复杂计算、素材细节和资源投入应服务于这些目标。
2. **让游戏状态统一驱动画面。** 分开组织规则与状态、显示与反馈、千星接口接入；可以在同一份 Lua 中用函数分区，无需额外框架。输入先转成动作，由规则更新状态，再驱动界面、动画和声音。分数、胜负和技能状态以游戏数据为准，不从显示文字或装饰动画反推；替换美术、关闭声音不应改变规则。
3. **明确阶段与资源归属。** 按玩法定义准备、游玩、暂停、结果及官方结算交接等必要阶段，规定各阶段接受哪些输入、推进哪些计时。结果只确认一次；重开重置本局状态，重复点击不能重复领奖或结算。每个控件、监听和播放实例都应有创建、复用、停止或清理的位置。
4. **让一次操作有完整反馈。** 对关键动作说明输入被接受、状态发生变化、过程持续及结束恢复各是什么表现；按玩法选择必要环节，不给每次点击堆特效。即时操作及时反馈，惯性与回弹平滑过渡；视觉、声音和实际结果来自同一事件，避免误导玩家或阻塞后续操作。
5. **按变化频率和重要性安排工作。** 静态数据预先计算，不变属性不重复写入；主体运动与输入连续处理，次要检查按需或低频执行。为控件、粒子、监听和单帧补算设置边界，优先复用。资源不足时先减少低优先级装饰，保留玩法正确性、关键反馈和确认的画风。
6. **先验证关键路径，再扩充细节。** 对新增或未核实的接入，先验证显示、一次核心操作、重置以及所需结算路径，再扩充资源与装饰；已经验证的配置直接复用。AI 内部可分步实现，默认仍向用户交付完整代码，不把中间原型或反复搭建当作额外必做步骤。可选声音或装饰缺失时保留基础玩法；关键模板或接口缺失时明确指出，不能静默假装成功。
7. **用证据收敛问题。** 为改动选择对应的可观察结果；视觉用同条件截图，手感看触发时序，性能看最忙阶段和连续重开的表现，结算看官方实际结果。先定位产生差异的环节，再修改相关参数或代码；分别报告静态检查、本地模拟和实机验证，避免一次改动多个无关因素后无法判断原因。
8. **复用约定与方法，参数随玩法决定。** 模板、宿主、信号和挂载构成可复用环境；步长、对象池容量、动画时长、镜头和难度参数集中配置，并按本次玩法验证。不要把某个示例的模拟频率、资源数量、操控方式或视觉偏好当成所有游戏的固定标准。

## 官方资料与接口核查

编写或修改接入代码前，核对本次涉及的接口。记录实际使用的类、字段或方法、参数、返回值及官方来源；项目中已有同版本、已核对的依据可以复用。版本变化、新增接口或行为不符时重新核实，不把每次游戏规则调整都变成重新查整套教程。

特别核对字段的读写权限、点号与冒号调用、事件回调参数、枚举类型、模板索引与运行时 ID、资源 ID 与播放实例 ID。按官方受限 Lua 环境编写，不混用浏览器、Unity 或其他 Lua 引擎接口。未确认的本地文件访问、协程、外部模块或资源导入能力，不默认可用。没有接口依据时说明缺口，不凭猜测给出可运行承诺。

用户验证的指南决定基础编辑器操作顺序，当前官方文档用于确认代码接口和新增能力。官方提供多个操作入口时，继续采用指南验证的入口；出现明确版本差异时，只调整受影响部分并说明依据。

这些资料由 AI 按本次功能查阅，无需人另行整理。基础搭建按[操作指南](editor-guide.md)执行；具体 Lua 接口和资源能力以当前官方开发文档为依据。同版本已核对的接口可以复用，新增能力、版本变化或运行行为不符时重新查证。

编写时尤其注意以下已核对事项，后续版本以对应官方页面为准：

- **运行环境有裁剪。** 当前文档为 Lua 5.3，`io.*`、`coroutine.*` 等能力不可用；不能照搬依赖这些能力的通用 Lua 代码。
- **接口存在不代表字段可写。** 例如图片的 `imageId` 为只读，应使用 `SetImage(...)`；控件激活和可见性通过对应设置方法修改。按接口签名区分 `game` 的点号调用与对象方法的冒号调用。
- **暂停影响不同回调。** `OnUpdate(dt)` 不受关卡时停影响，`OnLevelUpdate(dt)` 受影响。根据玩法选择更新方式，处理 `dt`，不要让速度依赖帧率。
- **模板索引与运行时 ID 用途不同。** 通过客户端模板根创建实例；不能将子控件索引、服务器控件索引或脚本 ID 当作可实例化的模板索引。
- **隐藏外层容器可能涉及销毁。** 官方说明外层客户端控件容器隐藏或销毁时，内部客户端控件会销毁；传送和重连也会重置。应区分外层容器操作与内层控件显隐，并处理清理或恢复。
- **声音与结算有各自的运行流程。** `PlayAudio2D(...)` 使用已配置的音效资源 ID，停止播放使用返回的实例 ID；本地显示胜利或收到回执都不能替代服务端执行官方结算。

AI 应在工作记录中保留本次接口依据与核查日期。官方页面无法读取或接口未找到时，先指出具体缺口，查找对应官方说明或让人提供该处文档，不把推测写成确定的代码或操作步骤。

## 概念图还原与清晰度

画风、清晰度及下一节的信息表达要求适用于实际游戏界面。用户希望先看概念图、已经提供参考图或要求视觉还原时，再使用本节的按图还原流程。已有确认图直接沿用，不重复确认，也不把概念图强制加入纯逻辑修改或排错任务。生成概念图前先考虑目标编辑器能力；用户已有图时说明可直接实现、需新增素材和仍待核实的部分。生成图片不等于资源已经导入游戏。

目标是将确认图转成由 Lua 驱动的可玩界面。AI 按以下方法工作，人继续执行[操作指南](editor-guide.md)第一部分的通用搭建步骤，无需手动排列大量图形。

### 画风与清晰度

以用户要求和确认图为准；没有指定画风时，优先使用轮廓平滑、文字清楚的二维图形。用户明确要求像素美术，或已确认像素风参考图时，才采用对应风格。“像素级还原”指高保真匹配参考图，不能理解为把画面改成像素风。

- **描述具体视觉目标。** 明确轮廓是否圆润、描边粗细、主体比例、阴影与高光层次；避免仅写“高清”“精美”。简单造型也应有完整轮廓和必要细节，不能为省事把主体替换成粗方块或棋盘式拼图。
- **选择适合轮廓的图形。** 使用已核实的圆形、椭圆等基础资源及组合形状，曲线分段应避免明显折角，同时遵守控件预算。保留参考图本来具有的硬边；需要精细插画质感时使用合适图片素材，不强行用大量小方格模拟。
- **区分设计尺寸与实际清晰度。** 1600×900 等数值是布局坐标基准，不等于素材像素或最终渲染分辨率。图片应按预计显示大小和最大放大倍率准备，在官方资源限制内选择足够尺寸；避免放大小尺寸缩略图，保持宽高比例。文字使用真实文本控件，并在最终显示大小下检查可读性。
- **平滑运动和边缘分别检查。** 运动按时间推进，避免将连续位置粗略量化到大网格。边缘粗糙时检查素材、放大比例和图形分段；只有官方接口明确支持时才能调整过滤、抗锯齿等设置，不能编造“高清模式”开关或 API。
- **用实际画面验收。** 在目标显示尺寸下查看主体轮廓、斜线、曲线接缝和文字，检查是否模糊、锯齿明显或出现意外像素块；还需检查运动中是否抖动。性能优化优先减少次要装饰和不可见对象，保持已确认画风，不擅自降低整幅画面分辨率或改成像素风。

**1. 提取可以实现的视觉规格。** 确定设计画布及比例，例如 16:9 下采用 1600×900；从图中提取视角、主体占屏比例、主要区域位置、留白、颜色、阴影方向和界面层级。以确认图和简短参数表作为基准，放入当前任务记录或代码配置，不另交付多套设计文档。概念图中画错或含糊的文字先按玩法纠正，实际显示用文本框，避免把可变数字和按钮文案烘焙进图片。

**2. 为每层选择合适的实现方式。**

| 画面内容 | 实现方式与取舍 |
|---|---|
| 色块、面板、简单图标和轮廓 | 用图片模板实例配合已核实的官方基础图形，通过尺寸、颜色、旋转和层叠组合；重复元素封装成绘制函数 |
| 简化的主体和景物 | 分解为轮廓、阴影、主体、局部高光，编成可复用组件；能一起移动或旋转的部分放在共同容器下 |
| 复杂纹理、插画背景、精细主体 | 使用适当的独立图片资源；先核实导入方式、格式、透明度、尺寸与资源引用方式，再生成或整理素材并指导人导入 |
| 运动、粒子、缩放、闪光和屏幕反馈 | 用代码按游戏事件驱动位置、旋转、缩放、透明度等已支持属性；合适时接入官方界面动效 |
| 文字和输入 | 用文字与点击模板承载真实文本、状态和交互区域，保持清晰和可操作 |

背景可以作为一张图，但会移动、变色、被点击或改变状态的主体需要独立处理；不能将整张概念图铺满屏幕就视为完成游戏。空心圆环要保留透明中心，曲线和不规则轮廓需选用合适资源或受预算约束的分段图形。新增图片属于额外资源步骤，不承诺所有美术升级都能仅靠替换 Lua 完成。

**3. 统一坐标与层级。** 在设计坐标中定义位置和尺寸，再映射到实际画布；保持主体和文字比例，避免非等比拉伸。背景、游戏世界、特效、信息界面和弹窗分层；输入坐标及点击区域与显示变换一致。宽高比变化时分别确定背景的铺满或裁切、界面的留边和锚点，确保按钮可见且能够点击。

**4. 让动态反馈与游戏状态一致。** 单张概念图只描述一个时刻，动画还需设计触发、峰值、衰减和结束。例如命中时立即闪光并产生粒子，能量变化同步更新进度，暂停时按玩法冻结运动，重开时清理残留。位移、镜头反馈、粒子和声音应跟随同一事件及状态；音效单独依赖有效官方资源，画面动画不依赖声音是否存在。

**5. 保留控件预算和流畅度。** 图形组合要计入容器及模板子控件开销，先核对当前官方上限并留余量。重复景物和粒子尽量复用，画面外对象按需隐藏或回收，避免每帧实例化。逼近预算时，优先合并静态细节、采用已支持的图片资源或降低次要装饰复杂度；保持主体、构图和关键反馈。不要为了增加纹理堆叠到控件上限。

**6. 用实际输出校准。** 有适合的本地工具时，可从实际 Lua 创建的控件树生成预览，提前发现布局和层级问题；本地模拟不等于官方渲染。最终以实机截图为准，先对齐画布比例与游戏状态，再检查构图、主体轮廓和大小、配色、文字、阴影与细节，动态场景检查对应触发阶段。逐项修正明显差异，不以独立制作的网页或新概念图替代 Lua 输出验收。

**还原说明：**基础图形适合还原构图、配色和简化造型；精细手绘纹理通常需要图片素材支持。字体、渲染方式和当前编辑器资源能力也会影响结果。应说明保留了哪些视觉特征、做了哪些简化及哪些仍未实测；未经同条件比对，不承诺或宣称像素级一致。

## 实际界面优先用视觉表达

**靠图形、控件造型和视觉层次表达信息，少堆说明文字。** AI 必须将这些要求落实到 Lua 生成的实际界面，包括游玩、暂停、结果及结算等待等状态；不能只改概念图或交付说明。

- **操作与状态可直接辨认。** 用图标、进度条、边缘高亮、按钮的可用／按下／禁用状态和留白表达信息。让玩家看得出主要目标、当前状态和下一步操作；不能仅靠大段说明补救不清楚的交互，也不只用颜色区分关键状态。
- **保留判断所需的文字。** 保留游戏目标、操作提示、关键按钮名称及分数、生命等玩法所需信息。图标含义不明确时配简短标签，不为了减少文字而隐去关键规则。
- **字体也要设计与实现。** 统一字体风格，为标题、正文、按钮和数值安排字号、字重、颜色及间距，避免过小、过细、拥挤或对比不足，确保清楚、饱满、易读。使用目标控件及 API 实际支持的字体和排版能力；先核对可写字段，不编造字体导入、字重或字距接口。
- **用实机截图与试玩验收。** 在目标设备和显示大小下检查文字裁切、重叠、换行、数字变化、信息层次及状态辨识；通过实际操作确认玩家能发现主要入口、理解反馈。本地预览不能替代 Lua 在原神中的实际效果，未实测的项目明确交接。

## 运动手感与性能

流畅度同时取决于运动与输入的处理方式，以及每帧的运行开销。以下是 AI 的实现要求，人按[操作指南](editor-guide.md)第 10 步提供试玩结果，不需要自行调整物理或性能参数。

先选择符合玩法的运动与碰撞模型，只计算必要状态。例如轨迹受约束时，可用路径进度、横向偏移和朝向描述主体，预先计算路径采样；自由移动的玩法则保留必要的二维位置、速度和碰撞关系。简化应保持玩法正确，不能忽略高速穿透等实际问题。

**1. 将时间推进与画面显示分开考虑。** 位置、速度、冷却和动画按时间更新，不能用“每帧固定移动若干像素”。有连续碰撞或对积分稳定性要求较高的玩法，可用固定步长模拟，再根据上一状态、当前状态和剩余时间插值显示位置与角度；简单玩法可直接使用适当的 `dt` 更新。步长按速度、碰撞精度与性能预算选取，不把某个游戏的高频设置套到所有玩法，也不将模拟频率宣称为实机 FPS。

长帧需要限制单帧补算量并明确剩余时间处理，避免补算越积越多。截断 `dt` 会丢弃时间；对倒计时、冷却和成绩计时，应明确使用模拟时间还是实际经过时间，并统一处理暂停和恢复。不能只为画面平稳就悄悄改变游戏计时规则。

**2. 平滑过渡要保留即时反馈。** 方向、侧向运动和镜头可按时间平滑追踪目标，例如用 `1 - exp(-k * dt)` 作为追踪比例；角度按最短方向过渡，避免跨越整圈时突然反转。将主体朝向与实际移动方向按玩法分别处理；需要惯性时使用速度和阻尼。爆发、命中等动作及时生效，再按曲线衰减；对应粒子、缩放和声音使用同一事件状态，避免显示与运动脱节。不要为了“丝滑”让输入响应或所有速度变化都变慢。

**3. 正确处理按下和松开。** 记录输入状态并识别按下边沿，避免长按事件重复触发一次性技能。固定模拟步可能漏掉极短操作时，按玩法增加小范围输入缓冲；持续动作松开后及时结束，不能因缓冲继续拖延。处理焦点变化和暂停时的残留按键。视觉插值通常会增加少量显示延迟，输入反馈应单独检查，不能仅凭轨迹平滑就认为手感正确。

**4. 把重复工作移出每帧循环。** 初始化时准备静态路径采样、形状数据、控件引用和常用颜色；按复杂度选择缓存、索引或查找方式，避免每帧重建全部场景或重复遍历控件树。文本、颜色、可见性等仅在值改变时写入。减少热路径中无必要的临时表、字符串和排序；优化优先针对可观察的开销，不要求完全零分配。

**5. 为景物与反馈设置有上限的复用池。** 粒子、拖尾、弹道和重复景物尽量复用已有控件；容量不足时淘汰过期或低优先级装饰，不能无限创建。视野筛选保留足够边缘余量，尤其要考虑快速运动和缩放，避免景物突然出现。可降低静态景物筛选的频率，只对新进入视野的对象重设资源与变换；已存在的世界容器仍随镜头连续移动。初始化成本也需检查，不能把运行期卡顿全部转移到开局。

**6. 限制累积开销并验证最忙的阶段。** 控件总数包含模板子控件、宿主和用户添加的动效，不能只数自己创建的根；为扩展留出余量。重开复用或重置状态，退出解除监听、停止声音并清理拥有的对象，避免多局后越来越慢。减少大面积透明层、过多粒子等实际渲染负担；达到数量限制以内不代表一定流畅。性能取舍优先保留主体、操作反馈和已确认画风。

按玩法选择必要的检查，并报告实际结果：

| 检查 | 观察什么 |
|---|---|
| 不同帧率与波动 | 本地条件允许时，用例如 30／60／120 FPS 的时间序列及长短交替帧推进同一操作；比较移动距离、碰撞、冷却、计时和插值连续性，容差应与玩法匹配 |
| 输入与过渡 | 短按能否被采到、松手是否及时、长按是否重复触发、角度跨界是否跳变、暂停恢复是否突进或保留错误输入 |
| 运行开销 | 开局、特效密集、快速移动和连续重开后，控件与监听数量是否稳定；有可用工具时记录帧耗时及尖峰，不只看平均 FPS |
| 实机复核 | 在目标设备和分辨率下重复相关场景；记录观察到的问题及数据来源，无法采集帧耗时时说明只能依据试玩或录屏观察 |

本地模拟能检查时间与逻辑一致性，无法证明原神客户端的真实渲染帧率。报告应区分代码中的措施、已完成的本地检查和已取得的实机证据，不承诺所有设备都不会卡顿。

## 动效与音效

**官方特效、动效和音效由 AI 查找并编写接入代码。** 涉及这些反馈时，先查官方资料并选择适合本次玩法的资源，完成事件触发、重复播放控制、停止和重新开始及退出时的清理。用户无需自己编写动画或声音逻辑；代码动画与资源音效分别实现。

| 要实现什么 | AI 去哪里找、查什么 |
|---|---|
| 界面中的完成提示、受击反馈等动效 | [界面动效控件](https://act.mihoyo.com/ys/ugc/tutorial/detail/mh2iyk9fa4gy)：资源选择与是否带声音；[客户端控件 API](https://act.mihoyo.com/ys/ugc/tutorial/detail/mhtakr07vej4)：`animationId`、`playSoundEffect`、`PlayAnimation()`、`StopAnimation()` 的类型、读写及调用方式 |
| 全屏氛围效果 | [全屏界面动效控件](https://act.mihoyo.com/ys/ugc/tutorial/detail/mhbn4i09l5ns)：覆盖全屏，默认在所有层级最下方，范围与层级不可更改；核对该控件支持的脚本接口，不能直接照搬普通界面动效的方法 |
| 按钮点击音效 | [预设按钮控件](https://act.mihoyo.com/ys/ugc/tutorial/detail/mhdbkf04v6y8)：音效配置；客户端控件 API 中 `clickAudioId` 所属类型。QX_Widget 的光标检测区域不能直接当作预设按钮使用 |
| 任务完成、拾取、警告等独立声音 | [客户端控件 API](https://act.mihoyo.com/ys/ugc/tutorial/detail/mhtakr07vej4)：`game.PlayAudio2D(audioId)`、返回的播放实例 ID，以及 `game.StopAudio(audioInstanceId)` 等停止与状态查询接口 |
| 三维场景中的特效和声音（仅有此需求时） | [特效播放组件](https://act.mihoyo.com/ys/ugc/tutorial/detail/mh4ppo02m1o8)、[音效播放器](https://act.mihoyo.com/ys/ugc/tutorial/detail/mhwiv89yra02)：组件依赖、资源选择和节点控制方式；场景组件接口不能直接当作二维 UI 的 Lua 接口 |

**资源名称和 ID 必须有来源。** 从可访问的官方编辑器资源选择器、已有工程配置或官方资源资料中主动取得，记录名称、ID、适用控件或组件及来源；资源用途根据实际资料和预览确定，不能猜 ID 或把示例数字当作可用资源。能取得的信息由 AI 自行查找，不把整套选资源、查接口和写逻辑的工作转交给用户。

接口核对记录（2026-10-05）：官方客户端控件 API 为普通界面动效列出了 `PlayAnimation()`、`StopAnimation()`；全屏动效条目只列出 `animationId`、`playSoundEffect` 字段，不能据此假定它也具有前两个方法，涉及播放控制时仍须核实。预设按钮的 `clickAudioId` 与独立声音接口也要按所属类型使用。

确实需要编辑器预先配置时，AI 给出最少且明确的入口、控件位置、资源选择和检查步骤，人只负责必要配置与试听。资源选择器不可访问或资料未提供具体 ID 时，说明缺少的资源信息，并只请人补充该处选择结果或现有配置；不能声称已完成查找。AI 能确认的信息不重复询问。查到资源不等于已经导入或配置到当前关卡，也不等于试听通过。

本流程的普通界面动效操作见[操作指南](editor-guide.md)第 9 步。AI 必须实现自动查找及相应事件触发，资源缺失时保留基础玩法；不能仅让人添加资源后自行补代码：

- **零个：**正常运行游戏和代码动画。
- **一个：**自动找到并作为通用反馈复用，不要求人填写动效 ID 或改控件名。
- **多个：**获取 GameRoot 的直接子控件，筛选界面动效，按 `GetSiblingIndex()` 升序保存。按照已确认的资源顺序与用途映射分别触发，不假定 `GetChildren()` 的返回顺序，不猜测哪个资源代表什么事件。

多动效由 AI 选择并安排时，自行记录资源顺序和用途映射；沿用用户配置且用途不明确时，才确认缺失的对应关系，不要求用户重复填写已知信息。尊重每个资源的音效开关，处理触发间隔、播放与停止、重开和退出时的清理。自动识别不意味着无需编写游戏事件与动效的关联。

代码动画和资源音效分别实现。未配置音效时保留游戏和代码动画；资源本身无声时，开启音效开关不会产生声音。使用独立声音接口时，核对资源 ID、播放实例 ID、停止与清理方式，不编造音效 ID。

## 输入生命周期与官方结算

- **控件与输入：**按模板和运行时类型寻找子控件，处理显示层级、布局适配、事件穿透、按下与松开、焦点变化及暂停恢复。主脚本只挂一次，模板和动态子控件不重复挂主脚本。
- **生命周期：**初始化避免重复创建与绑定；重开重置本局数据，清理或复用动态对象。退出解除本脚本创建的监听、停止声音、清理拥有的控件，并恢复自身修改的输入与时停状态。

### 官方结算必须落实到可执行代码

完整游戏的结束流程包含两个配套部分：AI 写好客户端 Lua 的请求与回执逻辑，人按操作指南第 4、5 步配置服务端结算图并添加到玩家模板。任何一侧缺失，都不能视为完成接入。服务端尚未搭好时，Lua 仍须包含完整接入代码，并将该配置明确交接给人；不能因此省略结算代码。

| 必须实现 | AI 在代码中检查什么 |
|---|---|
| 明确的成功条件 | 由游戏状态判断通关；无固定终点的玩法也要定义何时可成功完成游玩。失败、普通退出和重新开始不能误发成功请求 |
| 可到达的完成入口 | 通关后自动请求，或将可点击的“完成游玩”等入口绑定到请求函数。若保留自绘结果页和“再来一局”，必须同时提供完成游玩的路径；重开只重置本局 |
| 真实发送请求 | 从上述入口能追踪到已核对的官方客户端向服务端发送信号接口，实际使用 `COMPLETE_SIGNAL`（通用值 `MiniGame_Complete`）。函数必须被调用，不能只有常量、注释、占位或空实现；不能用仅在客户端内广播的事件替代 |
| 回执监听 | 在请求前通过已核对的官方接口注册 `SETTLEMENT_ACK_SIGNAL`（通用值 `MiniGame_SettlementAccepted`）处理。监听有效期覆盖请求等待阶段，不能发送后立即销毁宿主或解除监听 |
| 交接与防重复 | 发送前释放本脚本开启的时停，进入等待状态；防止连续点击、每帧判定或重复监听反复发送请求。重开重置本局结算状态，避免旧状态误触发新一局 |
| 超时与恢复 | 请求或回执异常时有有限等待、明确提示和受控重试，不能永久卡住或无限重发。重试前仍需满足成功条件，不得通过本地伪造回执绕过失败 |
| 官方完成判定 | 回执只表示服务端执行到了发送回执节点，不等于后续“结算关卡”已完成。自绘结果页和收到回执均不能作为实机成功证据；等待真实官方成功结算 |

**每次交付完整 Lua 前，沿实际调用路径检查一次：**通关条件 → 自动触发或完成按钮回调 → 结算请求函数 → 官方信号发送调用。另查回执注册、等待、超时及重试路径。只搜索到两个信号字符串不能证明接入完整。确认人应配置的服务端流程仍为：监听信号 → 设置玩家逃跑合法性 → 设置玩家结算成功状态 → 发送客户端脚本信号 → 结算关卡。

新建游戏和复用环境换玩法时，将结算接入与基础玩法一起实现；修改画面、输入或性能时保留已有接入，不用重写已验证的实现。发现缺失就先补齐并说明；仅有用户明确要求的概念图或临时演示不按完整游戏验收，不能由 AI 自行将完整游戏降为演示版。

**排查顺序：**若只有自绘结果页或按钮毫无反应，先检查 Lua 是否存在可到达的请求调用。若已实际发出请求但超时，先看玩家模板是否已添加结算图，再核对信号登记及节点选择、两类接线、回执处理、时停释放和“结算关卡”执行。客户端脚本文件名无需与信号同名；具体操作与 `.gia` 导出见操作指南第三部分。

## 代码交付与验证

默认交付一份可整段复制的完整 `.lua` 文件，填好两个模板 ID 和信号名；修改已有脚本后仍交付完整代码，除非用户明确要求差异片段。只做本次请求的交付，不额外生成页面或多套说明文档。

默认由人按操作指南第 7、8 步，新建客户端脚本、打开编辑器生成的关联文件、粘贴保存，然后到 GameRoot 添加脚本。AI 在可写工作区提供代码，不以直接修改原神数据目录为前提；用户另行要求直接代操作时，再按现有工具和权限执行。涉及新增资源时先核实支持情况，并附最少且准确的编辑器步骤；不让人拼接代码、手写布局或修改不能改名的子控件。

交付前进行可用的语法检查和与改动相关的必要逻辑检查。已有环境直接沿用，按需说明这次只需替换代码，或具体新增了哪些配置。附上最短试玩检查：显示、操作、重新开始、已配置的动效音效，以及官方成功结算；有视觉或性能改动时，采用前文对应检查。

交付与上传检查还须确认：正式人数设置为单人，不能用试玩人数代替；所用官方动效音效的资源来源和触发、停止、重开清理逻辑明确；Lua 实际界面的视觉表达与字体已有对应验收动作。用户只完成必要配置与试玩，AI 不将资源查找、代码实现或排版优化留给用户补做。

**官方结算是交付必检项，不能因用户只强调玩法或美术而跳过。** 检查上一节的实际调用路径；本地可模拟时，验证通关完成会发送请求、失败与重开不发送、连续点击不会重复请求、无回执时会超时并允许受控重试。检查发现漏接或不可达时，修复后再交付完整游戏。接口依据不足时明确缺口，不写猜测接口或用本地结果页冒充已接入。

交付说明用简短文字指出：结算由什么操作触发、请求和回执处理位于哪些函数、已做哪些检查、哪些仍需人实机确认。实现、配置和实机结果分别报告：代码接入已实现不等于玩家模板已配置，更不等于官方成功结算已验证。不能只写“支持结算”而不核对实际代码。

明确区分已执行的静态检查、本地模拟和原神实机验证。模拟通过不能证明官方接口或渲染性能已验证；需要人实机完成的环节明确交接。不能把“语法通过”写成“原神试玩通过”，也不能仅凭收到回执或显示自绘胜利画面宣称官方成功结算已完成。
